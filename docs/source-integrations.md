# Source and data integration

`install-integrations` locates declared generator and registry types, parses their Java syntax, and inserts hooks using actual loop iterables, accumulators, and declared output paths. Formatting, local variable names, completion-log text, and filenames do not select an insertion point. Enum JSON getter wrapping uses the same Java syntax tree instead of a regular-expression installer. Repeating installation leaves source unchanged.

`scripts/data-generator.gradle` selects Loom's merged jar configuration through the plugin's own class loader. During generator execution it identifies the vanilla jar on the resolved runtime classpath by its contents and reports the exact path. Prepare/finalize no longer assume a Loom cache directory or artifact filename. The data-generator revision remains pinned for reproducibility.

The registry lookup bridge discovers the unique public static zero-argument factory returning `HolderLookup.Provider`. It stops on ambiguity; there is no list of replacement factory names. The installer still recognizes the known generator call sites at that API boundary.

Before the target data generator is compiled, preparation compares the retained server jar with the resolved target jar. A referenced type that exists only in the retained jar is relocated when its public static constants have one target class that keeps a strict majority of those names. Instance members line up by property name: a field may become a no-argument method, and `Optional` or a single type-argument wrapper is unwrapped back to the original component. A no-argument call whose return type disappeared must have one replacement on the same receiver hierarchy whose type is the relocated value or its constant identity. When those constants are registry keys rather than instances, the unique vanilla lookup factory and the shortest type-aligned lookup chain resolve them. Ambiguous catalogs, members, accessors, or lookup chains stop generation before files are rewritten. The generator then emits the original property names from the relocated values. A chain of no-argument calls after an `Optional` unwrap runs only while the value is present, so a missing component stays absent instead of failing the generator. Repeating relocation leaves an already rewritten generator unchanged.

A nullable string factory that immediately forwards its argument to `Key.key` returns null when that argument is missing. That is the same result the factory already uses for an unknown key, and it lets a relocated optional component load without a stand-in value.

Typed scalar getter calls are wrapped when the installer can prove a complete iteration domain. `ScalarDataAccess` records values by unique `toString()` identities and captures bounded getter bytecode in `.nightstorm/scalar-data-accessors.json.gz`. If the getter disappears, its portable program evaluates current fields and no-argument methods, including bounded branches; old values are never substituted. Captured member descriptors must still match. When the program is unavailable, a unique public scalar getter must agree across every common baseline identity, with at least two distinct baseline values. Direct aliases of one field count as one candidate. Missing evidence, ambiguous candidates, unsupported programs, and changed member types stop generation. This replaces the named block-state fallback; stable identities and the typed builder/loop boundary remain requirements.

`DataShapeScanner` discovers component and attribute registrations from source and writes `.nightstorm/data-shapes.json`. For supported list-backed record codecs, it verifies that the encoder's field order agrees with the decoding constructor. The data normalizer uses that order and scalar type instead of a configured pot-side order. It accepts primitive leaves and single-property primitive wrappers; this is a bounded structural conversion, not proof of arbitrary wrapper semantics.

`DataMigration` replaces the three explicit JSON conversions with file/path-scoped rules learned from complete identity-matched baseline profiles. Supported projections are identity renames, path basenames, and object unwrapping guarded by unchanged primitive properties. Every sample must agree, and ambiguous projections fail before files are written. Namespace keys share a wildcard path; array positions cannot establish identity. Rules persist in `.nightstorm/data-migrations.json` and apply to current values. They demonstrate correspondence on the observed baseline rather than proving arbitrary semantic equivalence. New object shapes outside a saved unwrapping guard remain intact; unsupported projections need further evidence and implementation. Prepare captures the retained data version first when older streams lack migration metadata.

Java/Gradle/Minecraft API vocabulary, the retained registration types, version-catalog keys, Gradle dependency edits, Javadoc edits, and the source palette-width constant remain explicit integration boundaries. The palette width itself is derived from generated state IDs rather than a fixed number.

Regression tests exercise renamed files and locals, formatting changes, repeated installation, unrelated record layouts and JSON keys, changed current scalar values, ambiguous getter/projection evidence, mismatched scalar data, and contradictory constructors. The workflow runs the engine tests before planning an update.
